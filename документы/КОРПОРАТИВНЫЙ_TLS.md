# Корпоративная TLS-интеграция Лексуса

**Статус:** первый необязательный инструмент диагностики. Это не сертифицированное СКЗИ, не замена КриптоПро CSP и не подтверждение соответствия требованиям банковской или государственной информационной системы.

## Зачем

Для корпоративной разработки часто недостаточно просто открыть HTTPS-соединение: требуется проверить цепочку X.509, срок действия сертификата, имя сервера, клиентский сертификат и двустороннюю TLS-аутентификацию (mTLS).

Лексус добавляет отдельный инструмент `лексус-сертификаты`. Он не изменяет старый интерпретатор, системное хранилище доверия или основной загрузочный бинарник.

## Сборка

Нужен OpenSSL 3.0 или новее и `pkg-config`.

Linux (Debian/Ubuntu):

```sh
sudo apt install build-essential pkg-config libssl-dev
make -C ядро tls-tools
```

MSYS2 UCRT64:

```sh
pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-openssl mingw-w64-ucrt-x86_64-pkgconf
make -C ядро tls-tools
```

Это отдельная необязательная цель. Основные команды остаются прежними:

```sh
make -C ядро
make -C ядро test
```

Они не требуют OpenSSL. Новый инструмент проверяется отдельно:

```sh
make -C ядро tls-test
```

## Команды

Посмотреть доступные сценарии:

```sh
./ядро/лексус-сертификаты профили
```

Прочитать сертификат PEM или DER, показать владельца, издателя, срок действия, алгоритм ключа и SHA-256 отпечаток:

```sh
./ядро/лексус-сертификаты инфо сертификат.cer
```

Проверить цепочку: конечный сертификат, корневой CA и необязательный промежуточный CA:

```sh
./ядро/лексус-сертификаты проверить сайт.cer russian_trusted_root_ca.cer russian_trusted_sub_ca.cer
```

Проверить клиентский PKCS#12-контейнер:

```sh
./ядро/лексус-сертификаты p12 клиент.p12
```

Пароль вводится в интерактивном терминале без отображения. Он не должен передаваться в аргументах командной строки. Инструмент проверяет MAC контейнера и соответствие закрытого ключа открытому ключу сертификата. Ключ не печатается и не экспортируется в отдельный файл.

Проверить TLS-сервер по системным CA:

```sh
./ядро/лексус-сертификаты tls api.example.ru
```

Добавить явно выбранный CA-файл:

```sh
./ядро/лексус-сертификаты tls api.example.ru 443 --корень russian_trusted_root_ca_pem.crt
```

Подключиться с клиентским сертификатом mTLS:

```sh
./ядро/лексус-сертификаты tls api.example.ru 443 --корень sber_ca_bundle.pem --клиент-p12 sber-client.p12
```

Для TLS-подключения проверяются цепочка сервера и соответствие имени узла сертификату. Минимальная версия — TLS 1.2. При передаче `--корень` файл должен быть PEM-бандлом. DER-файл можно преобразовать локально:

```sh
openssl x509 -inform DER -in russian_trusted_root_ca.cer -out russian_trusted_root_ca.pem
```

## Профиль Минцифры / Russian Trusted CA

На портале Госуслуг опубликованы корневой `Russian Trusted Root CA` и промежуточные `Russian Trusted Sub CA`; для разных платформ и периодов выпуска могут встречаться дополнительные промежуточные сертификаты и варианты RSA/ГОСТ.

Скачивайте набор только с официального портала:

- https://www.gosuslugi.ru/crt

Не следует брать корневые сертификаты из писем, мессенджеров, форумов или случайных репозиториев. Не устанавливайте их автоматически в системное хранилище без отдельного решения администратора: добавление корневого CA расширяет доверие всех приложений, использующих это хранилище.

Для RSA-цепочки можно явно передать корневой PEM-файл в `--корень` или в команду `проверить`. Поддержка сертификатов ГОСТ зависит от криптографического провайдера, который способен проверить подпись соответствующим алгоритмом. Обычная сборка OpenSSL не должна считаться готовой поддержкой ГОСТ только потому, что она прочитала файл сертификата.

## Профиль Сбер API

В документации Sber API описана взаимная TLS-аутентификация: клиент использует собственный контейнер PKCS#12 (`.p12`), а серверная цепочка доверия должна включать удостоверяющие центры Сбера и Минцифры.

Инструмент помогает:
- проверить, что PKCS#12 открывается и контрольная сумма подтверждена;
- убедиться, что клиентский закрытый ключ соответствует сертификату;
- посмотреть владельца, издателя и срок действия;
- использовать этот контейнер в диагностическом mTLS-подключении.

Сертификат Сбер API связан с конкретным `clientId`; не переносите один контейнер между разными сервисами без подтверждения в кабинете Сбера. Не храните пароль в исходнике, командной строке, Git, логах или конфигурации открытым текстом. Для рабочей системы используйте утверждённое организацией хранилище ключей или аппаратный носитель.

Актуальная документация:
- https://developers.sber.ru/docs/ru/sber-api/start/tls
- https://developers.sber.ru/docs/ru/sber-api/start/tls-create

## Профиль ГОСТ TLS и электронная подпись

Это отдельная задача от установки корневого сертификата. Для соединений, где сервер требует российские криптографические наборы TLS, необходим совместимый браузер/сетевой стек и сертифицированный криптопровайдер. В типичном пользовательском окружении это КриптоПро CSP и совместимая интеграция браузера или сервера.

Лексус **не реализует криптографические алгоритмы ГОСТ самостоятельно**, не обходит CryptoPro и не подменяет его самодельной реализацией. В первом этапе OpenSSL-инструмент проверяет только те алгоритмы, которые доступны его установленной сборке. Если сертификат или TLS-профиль требует ГОСТ-провайдер, используйте штатную интеграцию КриптоПро CSP и соответствующий официальный браузерный/серверный компонент.

Документация:
- https://cryptopro.ru/products/csp
- https://cryptopro.ru/products/csp/tls
- https://yandex.ru/support/browser/ru/tls/tls

## Границы и безопасность

- Это диагностика TLS/X.509 и mTLS, не средство выпуска или подписания квалифицированной электронной подписи.
- Инструмент не устанавливает CA-сертификаты в Windows, macOS, Linux или браузер.
- Инструмент не загружает сертификаты из интернета и не закрепляет один отпечаток CA навсегда.
- Для соединений используются системные пути доверия OpenSSL и явно переданный CA-файл.
- В текущем этапе нет проверки отзыва через OCSP/CRL, работы с ГОСТ TLS или прямого API к КриптоПро CSP.
- PKCS#12 закрытый ключ разбирается только в памяти процесса; его нельзя считать защищённым аппаратным хранилищем.
- Успешная проверка сертификата не является аудитом всей инфраструктуры и не означает соответствие ФСТЭК, ФСБ, PCI DSS или внутренним требованиям организации.
- До подключения авторизации по возможностям к VM этот инструмент не создаёт песочницу для программ Лексики.

Основной движок и его старые механизмы не меняются этим инструментом. OpenSSL — необязательная внешняя зависимость только для корпоративного TLS-адаптера.
