# Архитектура самостоятельного движка Лексики

## Цель производительности
Лексика должна стать системным языком общего назначения: нативные исполняемые файлы,
низкие накладные расходы, эффективная работа с памятью, конкурентность и оптимизация.
Сравнение с C++ — целевой класс задач, а не обещание одинаковых бенчмарков до появления
компилятора, ABI, оптимизатора и воспроизводимых измерений.

## Целевая архитектура
1. Фронтенд: UTF-8 lexer, морфологический анализатор, parser и типизатор. Результат —
   собственное типизированное промежуточное представление (ЛПП), не AST старого Python.
2. IR: SSA-подобные блоки, явные типы, эффекты и контроль потока. Оптимизации:
   constant folding, dead-code elimination, inlining, common-subexpression elimination,
   escape analysis и specialization динамических участков.
3. Машина: собственная VM с верифицируемым байткодом, register-based execution,
   компактными 8-байтовыми инструкциями, таблицами констант и метаданными отладки.
   Первый нативный модуль уже содержит регистры, арифметику, сравнение, условные
   переходы, возврат, проверку регистров/адресов и лимит шагов. VM — переносимый
   bootstrap и fallback, а не потолок производительности.
4. Нативный backend: сначала собственный portable backend для x86-64 и AArch64,
   далее ABI и объектные файлы. C не является постоянным генератором кода и не задаёт
   семантику языка.
5. Runtime: собственные значения, аллокатор, арены временных объектов, generational GC
   для ссылочных графов, escape analysis и явное владение для системного кода.
   Малые значения хранятся inline; горячие пути не должны выделять память без нужды.
6. Стандартная среда: OS API через узкий слой возможностей, без утечки платформенных
   типов в язык.
7. Самохостинг: компилятор, VM и стандартная библиотека постепенно переписываются
   на Лексике. C11 остаётся только bootstrap до способности языка собрать себя.

## Режимы памяти
- По умолчанию — трассируемый generational/incremental GC для удобства.
- Системный режим — явные области/арены и проверяемое владение для предсказуемой задержки.
- Никаких обязательных heap allocation для чисел и малых значений.
- Сборщик измеряется по паузам, allocation rate, retained heap и fragmentation.

## Встроенный словарь
Источник danakt/russian-words закреплён на commit
d68c007fe9260d2d40ce413f13f77335c5af1e62 (MIT). Он подключается как pinned submodule
только для подготовки релиза. Нативный сборщик преобразует CP1251 в UTF-8, нормализует
регистр, фильтрует некорректные строки, сортирует и удаляет дубликаты, затем пишет
формат LEKSLXD1: версия, количество, размер, CRC32, таблица смещений и блок UTF-8 слов.
В пользовательском runtime нет исходного TXT, CP1251, Python, сетевого запроса или
импортёра. В поставку попадает готовый индекс и MIT notice. Поиск — O(log N), подсказки
— O(log N + K). Словарь помогает подсказкам и диагностике, но не запрещает неизвестные
пользовательские имена.

## Этапы
A. Исполняемые проверки контракта и модель значений.
B. Бинарный индекс, интеграция в нативный лексер и подсказки.
C. Удаление Python из запуска: lexer/parser/compiler/VM/stdlib на нативном bootstrap.
D. Перенос bootstrap-компилятора на Лексику и self-hosting.
E. Оптимизирующий IR и native backends x86-64/AArch64.
F. Память, FFI, потоки, профилировщик и пакеты Windows/Linux/macOS/Android.

## Честный статус
Нативный лексус.c пока не исполняет .lek целиком. Основная грамматика, исполнитель
и сборщик Windows всё ещё используют Python. Этот этап добавляет инфраструктуру
словарного индекса, но не объявляет Лексику независимой или сравнимой с C++ по скорости.
