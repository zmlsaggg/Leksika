# Выпуск релизов Лексики

Этот документ задаёт ручной порядок публикации GitHub Release. Он не означает, что текущая версия уже готова к стабильному выпуску.

## Когда выпускать

- Используйте предварительные версии `0.x.y-alpha.N` или `0.x.y-beta.N`, пока интерфейсы, формат файлов или рантайм активно меняются.
- Используйте `1.0.0` только после документированной проверки установки, обратной совместимости и основного сценария запуска на поддерживаемых платформах.
- Не присваивайте тег сборке, которую фактически не проверяли.

## Подготовка

1. Обновите `CHANGELOG.md` и укажите заметные изменения, исправления и известные ограничения.
2. Проверьте примеры и документацию.
3. Запустите проверки языка и нативного ядра по актуальным инструкциям проекта.
4. Проверьте установщик на чистой системе соответствующей платформы.
5. Убедитесь, что в пакет не попали токены, ключи, локальные конфигурации, временные файлы и отладочные данные.
6. Проверьте лицензию и состав распространяемых сторонних компонентов.

## Версионирование и тег

Используйте Semantic Versioning: `MAJOR.MINOR.PATCH`. Для предварительных выпусков добавляйте суффикс, например `0.3.0-beta.1`.

Создайте аннотированный Git-тег на проверенном commit:

```sh
git tag -a v0.3.0-beta.1 -m "Leksika v0.3.0-beta.1"
git push origin v0.3.0-beta.1
```

Тег должен указывать именно на исходный код, из которого собраны приложенные файлы.

## Артефакты

Прикладывайте только реально собранные и проверенные файлы. Для каждого артефакта опубликуйте SHA-256:

```sh
sha256sum <artifact>
```

На Windows контрольную сумму можно получить командой:

```powershell
Get-FileHash .\<artifact> -Algorithm SHA256
```

Не заявляйте о наличии сборок для платформ, которые не были проверены. Не прикладывайте бинарные файлы, собранные из другого commit.

## Release notes

Каждый выпуск должен содержать:
- краткое описание;
- новые возможности;
- исправления;
- несовместимые изменения;
- известные ограничения;
- поддерживаемые платформы и требования;
- инструкции обновления;
- перечень приложенных файлов и SHA-256.

## Публикация через GitHub

1. Откройте **Releases → Draft a new release**.
2. Выберите существующий проверенный тег.
3. Укажите заголовок версии и заполните release notes.
4. Загрузите проверенные артефакты и файл контрольных сумм.
5. Отметьте выпуск как **pre-release**, если версия имеет alpha/beta/rc статус.
6. Проверьте страницу опубликованного релиза и скачивание каждого файла.

Пока отдельный пакетный реестр не реализован, GitHub Releases является рекомендуемым каналом распространения готовых сборок.
