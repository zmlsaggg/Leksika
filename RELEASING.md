# Выпуск релизов Лексики

Этот документ описывает автоматический предварительный канал и ручной порядок выпуска версий. Он не означает, что текущая версия уже готова к стабильному выпуску.

## Автоматический nightly

На каждый push в `main` workflow `.github/workflows/release.yml` для того же
коммита запускает полный native CI, собирает `leksika.exe`, проверяет SHA-256 и
устанавливает, запускает и удаляет именно этот файл на чистом Windows runner.
Только после успеха обновляется **предварительный** релиз `nightly` с файлами
`leksika.exe` и `SHA256SUMS.txt`. Устаревший запуск не публикуется поверх нового
`main`. Релиз не удаляется заранее; предыдущая сборка остаётся, если проверка
или сборка не прошла. Релиз `latest` больше не перезаписывается автоматически.
Автоматика сейчас публикует только Windows; проверенные Linux/macOS пакеты для
релиза ещё не реализованы. Alpha/beta/rc и стабильные версии запускаются вручную
через workflow_dispatch: создайте тег `vX.Y.Z[-alpha.N|-beta.N|-rc.N]` на
текущем `main`, затем укажите версию без `v`. Workflow проверяет SHA тега,
повторяет CI и smoke-тест и создаёт неизменяемый релиз. Пустое поле выпускает
nightly. Release notes и поддержка других платформ по-прежнему требуют
проверки и дополнения вручную.

Windows EXE не подписан сертификатом издателя. Браузер, антивирус или Windows
SmartScreen могут предупреждать или блокировать его: имя файла и SHA-256 этого
не исправляют. Не советуйте пользователям отключать защиту. Для уменьшения таких
предупреждений потребуется проверенный code-signing сертификат, подписывание
итогового артефакта и проверка подписи и установки, а репутация у Microsoft и
браузеров формируется отдельно; даже подпись не гарантирует отсутствие блокировки.
Сертификат и ключи не хранятся в репозитории. Механизм подписывания ещё не
настроен: контейнер установщика читает трейлер в конце файла, поэтому
совместимость Authenticode с ним надо сначала реализовать и проверить на Windows.
Сумма SHA-256 обнаруживает изменение файла при передаче, но не подтверждает
автора, если источник суммы тоже мог быть подменён.

## Когда выпускать

- Используйте предварительные версии `0.x.y-alpha.N` или `0.x.y-beta.N`, пока интерфейсы, формат файлов или рантайм активно меняются.
- Используйте `1.0.0` только после документированной проверки установки, обратной совместимости и основного сценария запуска на поддерживаемых платформах.
- Не присваивайте тег сборке, которую фактически не проверяли.

## Подготовка

1. Обновите `CHANGELOG.md` и укажите заметные изменения, исправления и известные ограничения.
2. Проверьте примеры и документацию.
3. Запустите проверки языка и нативного ядра по актуальным инструкциям проекта.
4. Проверьте установщик на чистой системе соответствующей платформы.
5. Убедитесь, что в пакет не попали токены, ключи, локальные конфигурации, временные файлы и отладочные данные.
6. Проверьте лицензию и состав распространяемых сторонних компонентов.

## Версионирование и тег

Используйте Semantic Versioning: `MAJOR.MINOR.PATCH`. Для предварительных выпусков добавляйте суффикс, например `0.3.0-beta.1`.

Создайте аннотированный Git-тег на проверенном commit:

```sh
git tag -a v0.3.0-beta.1 -m "Leksika v0.3.0-beta.1"
git push origin v0.3.0-beta.1
```

Тег должен указывать именно на исходный код, из которого собраны приложенные файлы.

## Артефакты

Прикладывайте только реально собранные и проверенные файлы. Для каждого артефакта опубликуйте SHA-256:

```sh
sha256sum <artifact>
```

На Windows контрольную сумму можно получить командой:

```powershell
Get-FileHash .\<artifact> -Algorithm SHA256
```

Не заявляйте о наличии сборок для платформ, которые не были проверены. Не прикладывайте бинарные файлы, собранные из другого commit.

## Release notes

Каждый выпуск должен содержать:
- краткое описание;
- новые возможности;
- исправления;
- несовместимые изменения;
- известные ограничения;
- поддерживаемые платформы и требования;
- инструкции обновления;
- перечень приложенных файлов и SHA-256.

## Публикация через GitHub

1. Откройте **Releases → Draft a new release**.
2. Выберите существующий проверенный тег.
3. Укажите заголовок версии и заполните release notes.
4. Загрузите проверенные артефакты и файл контрольных сумм.
5. Отметьте выпуск как **pre-release**, если версия имеет alpha/beta/rc статус.
6. Проверьте страницу опубликованного релиза и скачивание каждого файла.

Пока отдельный пакетный реестр не реализован, GitHub Releases является рекомендуемым каналом распространения готовых сборок.


## GitHub Releases и GitHub Packages

Это два разных способа распространения:

- **GitHub Releases** — версии программы, привязанные к Git-тегу. Сюда прикладываются готовые установщики и архивы: например, Windows `.exe`, архив Linux/macOS и файл `SHA256SUMS.txt`.
- **GitHub Packages** — реестры для конкретных форматов пакетов. GitHub поддерживает npm, RubyGems, Maven/Gradle, NuGet и Container/OCI (Docker). Это не универсальное хранилище для произвольных `.exe` и `.zip`.

У Лексики пока нет собственного пакетного менеджера и совместимого с GitHub Packages формата. Поэтому готовые сборки следует публиковать через **Releases**; раздел Packages пока можно оставить пустым. Публиковать контейнер в GHCR имеет смысл только при появлении отдельного официального Docker-сценария — он не заменит обычный установщик.

Документация GitHub:
- [О GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
- [О GitHub Packages и поддерживаемых реестрах](https://docs.github.com/en/packages/learn-github-packages/introduction-to-github-packages)

Установщик содержит стандартный ресурс версии (`сборка/установщик.rc`) и не
использует UPX; версия ресурса 0.1.0.0 — версия загрузчика, а не номер Git-тега.
При подозрении на ложное срабатывание отправьте **конкретный SHA-256 и файл**
через [Microsoft Security Intelligence](https://www.microsoft.com/en-us/wdsi/filesubmission)
и, при необходимости, производителям других антивирусов. Результат и сроки
зависят от вендора. Метаданные не удостоверяют издателя и не гарантируют,
что браузер или антивирус перестанет предупреждать.

### Дополнительные компоненты установщика

Графический установщик показывает фактическую папку `%LOCALAPPDATA%\Лексус`,
прогресс по объёму распакованных файлов и приблизительное оставшееся время
распаковки; финальные 10% отведены самопроверке и настройке. Скорость диска и
самопроверка влияют на общее время. Тихая установка не открывает страницы и не
изменяет хранилище сертификатов.

Необязательные пункты по умолчанию выключены. Пока они **только открывают страницы**
после успешной установки, а не скачивают модели и не устанавливают сертификаты:
Госуслуги, GigaChat 3.1 10B и YandexGPT 5 Lite 8B. Модели занимают несколько
гигабайт, требуют совместимый llama.cpp и отдельную настройку внешней модели
Лексики (см. README). Доступность ссылок и версий llama.cpp при выпуске нужно
проверять отдельно. Корневые сертификаты расширяют доверие системы, поэтому
на странице показывается предупреждение, а решение об установке остаётся за
пользователем. Автоматическую загрузку и проверку целостности моделей и
сертификатов ещё предстоит реализовать и проверить на Windows.
