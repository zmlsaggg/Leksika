# Выпуск релизов Лексики

Этот документ описывает автоматический обновляемый выпуск и порядок выпуска
отдельных версий. Статус GitHub «Release» не означает, что все компоненты уже
достигли полной совместимости: нативное ядро по-прежнему экспериментальное.

## Автоматическая сборка

Каждый push в `main` запускает проверку и сборку одного комплекта из того же
коммита: Windows-установщик, Android APK с учебной песочницей и экспериментальное нативное ядро для Windows x64,
Linux x64, macOS arm64 и x64, Android arm64. После Windows smoke-теста,
Android smoke-теста и проверки комплекта обновляется выпуск с тегом `nightly`.
Он отмечен как обычный Release и Latest, но остаётся **обновляемой сборкой**,
не неизменяемой версией. Релизные заметки указывают исходный коммит и ограничения.
Устаревший запуск не публикуется поверх нового `main`. Загрузка на GitHub
производится пофайлово: при ошибке сети возможен неполный комплект, такую ошибку
нужно исправить повторным запуском workflow; не считайте это атомарной заменой.

`zz-SHA256SUMS.txt` охватывает установщик, APK и все пять архивов; `zz-checksums.txt`
содержит отдельно суммы архивов для шаблонов Scoop/Homebrew. Два автоматически
созданных GitHub архива исходного кода не являются сборками для платформ.
Android-архив содержит консольный бинарник и не заменяет APK. APK работает
без сети внутри WebView и исполняет учебное подмножество языка. Подписывается
временным ключом каждой сборки; без постоянного ключа обновление поверх предыдущей
версии невозможно, потребуется удалить приложение. Подпись не подтверждает
издателя. Для надёжного выпуска необходимо отдельно настроить постоянный ключ
подписи, хранящийся вне репозитория. Проверяется установка и запуск примера в
эмуляторе; на физическом устройстве тестирования пока не было.

При push тега `vX.Y.Z[-alpha.N|-beta.N|-rc.N]` или ручном запуске на `main`
с указанной версией тот же комплект публикуется отдельным версионным выпуском.
Без суффикса выпуск обычный, alpha/beta/rc остаются pre-release. Для ручного
запуска тег должен уже указывать на тот же commit, что и `main`. Проверяется
отсутствие существующего релиза; черновик публикуется автоматически сразу после
всех сборок, тестов и загрузки — готовый выпуск не остаётся черновиком. При сбое
загрузки черновик остаётся для проверки, повторный запуск не перезаписывает его.
Проверка эмулятора Android (`android-smoke`) входит в прогон, но не блокирует
публикацию: сборка APK и его установка проверяются отдельно. Расширение для
редактора (`leksika-language.vsix`) собирается в том же прогоне и прикладывается
к релизу вместе с контролем суммы.

Архивы `leksika-native-*` содержат **экспериментальное C11-ядро**, а не полный
Python-совместимый runtime: supported subset работает без Python, остальное не
подменяется автоматически. Есть пример и индекс словаря; при обращении к словарю
нужно указать путь явно. `zz-checksums.txt` содержит SHA-256 всех архивов, а
`zz-SHA256SUMS.txt` — всех файлов комплекта, включая расширение редактора. Linux собран на Ubuntu 24.04 и требует glibc
2.39 или новее; macOS без подписи и notarization. Android — PIE с системной библиотекой Bionic
для arm64/API 24+, проверяется в эмуляторе Android 15 с трансляцией ARM64, не в Termux или на
реальном устройстве: совместимость с ними ещё не подтверждена. Шаблоны Scoop
и Homebrew и инструкции для отдельных bucket/tap: `packaging/README.md`;
автоматическое обновление tap и bucket описано в разделе
«Пакетные менеджеры: Homebrew и Scoop».

Windows EXE не подписан сертификатом издателя. Браузер, антивирус или Windows
SmartScreen могут предупреждать или блокировать его: имя файла и SHA-256 этого
не исправляют. Не советуйте пользователям отключать защиту. Для уменьшения таких
предупреждений потребуется проверенный code-signing сертификат, подписывание
итогового артефакта и проверка подписи и установки, а репутация у Microsoft и
браузеров формируется отдельно; даже подпись не гарантирует отсутствие блокировки.
Сертификат и ключи не хранятся в репозитории. Механизм подписывания ещё не
настроен: контейнер установщика читает трейлер в конце файла, поэтому
совместимость Authenticode с ним надо сначала реализовать и проверить на Windows.
Сумма SHA-256 обнаруживает изменение файла при передаче, но не подтверждает
автора, если источник суммы тоже мог быть подменён.

## Когда выпускать

- Используйте предварительные версии `0.x.y-alpha.N` или `0.x.y-beta.N`, пока интерфейсы, формат файлов или рантайм активно меняются.
- Используйте `1.0.0` только после документированной проверки установки, обратной совместимости и основного сценария запуска на поддерживаемых платформах.
- Не присваивайте тег сборке, которую фактически не проверяли.

## Подготовка

1. Обновите `CHANGELOG.md` и укажите заметные изменения, исправления и известные ограничения.
2. Проверьте примеры и документацию.
3. Запустите проверки языка и нативного ядра по актуальным инструкциям проекта.
4. Проверьте установщик на чистой системе соответствующей платформы.
5. Убедитесь, что в пакет не попали токены, ключи, локальные конфигурации, временные файлы и отладочные данные.
6. Проверьте лицензию и состав распространяемых сторонних компонентов.

## Версионирование и тег

Используйте Semantic Versioning: `MAJOR.MINOR.PATCH`. Для предварительных выпусков добавляйте суффикс, например `0.3.0-beta.1`.

Создайте аннотированный Git-тег на проверенном commit:

```sh
git tag -a v0.3.0-beta.1 -m "Leksika v0.3.0-beta.1"
git push origin v0.3.0-beta.1
```

Тег должен указывать именно на исходный код, из которого собраны приложенные файлы.

## Артефакты

Прикладывайте только реально собранные и проверенные файлы. Для каждого артефакта опубликуйте SHA-256:

```sh
sha256sum <artifact>
```

На Windows контрольную сумму можно получить командой:

```powershell
Get-FileHash .\<artifact> -Algorithm SHA256
```

Не заявляйте о наличии сборок для платформ, которые не были проверены. Не прикладывайте бинарные файлы, собранные из другого commit.

## Release notes

Каждый выпуск должен содержать:
- краткое описание;
- новые возможности;
- исправления;
- несовместимые изменения;
- известные ограничения;
- поддерживаемые платформы и требования;
- инструкции обновления;
- перечень приложенных файлов и SHA-256.

## Публикация через GitHub

1. Откройте **Releases → Draft a new release**.
2. Выберите существующий проверенный тег.
3. Укажите заголовок версии и заполните release notes.
4. Загрузите проверенные артефакты и файл контрольных сумм.
5. Отметьте выпуск как **pre-release**, если версия имеет alpha/beta/rc статус.
6. Проверьте страницу опубликованного релиза и скачивание каждого файла.

Пока полный установщик доступен только через GitHub Releases, они остаются основным каналом готовых сборок.


## Публикация на PyPI

Пакет `leksika` — это переходный исполнитель на Python 3.8+, то есть тот же
движок, что и `./Leksika`, но поставленный через `pip`. Нативного ядра,
значков и медиафайлов в нём нет; полный набор по-прежнему даёт установщик из
релизов.

```sh
python3 -m pip install --user leksika
leksika справка
leksika запустить пример.lek
```

Кроме него ставятся псевдонимы `leksus` и `lek`. Исходники `.lek` лежат внутри
пакета (`leksika_engine/runtime/`), поэтому пользователю не нужен Git-клон.

Пакет собирается по `pyproject.toml` (hatchling), а публикуется только
файлом `.github/workflows/publish.yml` через доверенную публикацию
(Trusted Publishing, OpenID Connect). Пароли и API-токены не нужны и не
хранятся в секретах репозитория.

### Разовая настройка доверенного издателя

1. Создайте окружения репозитория **Settings → Environments**: `pypi` и,
   если планируете проверять выпуск на TestPyPI, `testpypi`. Для `pypi`
   включите Required reviewers, чтобы публикация ждала ручного подтверждения.
2. Откройте https://pypi.org/manage/account/publishing/ и добавьте издателя
   для ещё не созданного проекта («pending publisher»):

   | Поле | Значение |
   | --- | --- |
   | PyPI Project Name | `leksika` |
   | Owner | `zmlsaggg` |
   | Repository name | `Leksika` |
   | Workflow name | `publish.yml` |
   | Environment name | `pypi` |

3. Для проверок повторите то же на
   https://test.pypi.org/manage/account/publishing/, указав Environment name
   `testpypi`.

`Workflow name` — это имя файла в каталоге `.github/workflows/`, без каталога
и без расширения-подстановки: ровно `publish.yml`. Если файл переименовать,
публикация перестанет работать, пока имя не поправят и на PyPI: индекс
сверяет владельца, репозиторий, файл процесса и окружение одновременно.
Значения по умолчанию вроде `workflow.yml` не подходят — такого издательского
файла в репозитории нет.

### Что происходит при выпуске

- `git push origin v0.4.0-beta.1` запускает `publish.yml`; запрос из PR только
  собирает и проверяет пакет, но ничего не публикует.
- Проверки: тег формата `vX.Y.Z[-alpha.N|-beta.N|-rc.N]`, тег указывает на
  коммит из `main`, версия ещё не занята в целевом индексе, а `release.yml`
  для того же коммита уже завершился успешно. Иначе workflow завершится
  ошибкой до сборки.
- Сборка: версия из тега переводится в PEP 440 (`v0.4.0-beta.1` → `0.4.0b1`),
  собираются sdist и wheel, выполняется `twine check --strict`, проверяется
  состав колеса и установка в чистом окружении с запуском примеров.
- Публикация: отдельное задание с `id-token: write` и окружением `pypi`
  (или `testpypi`). После загрузки суммы SHA-256 сверяются с ответом JSON API
  индекса, чтобы успешный ответ об отправке не подменял проверку.
- Аттестации PEP 740 (Sigstore) прикладываются автоматически и видны на
  странице файлов проекта.

Ручной запуск (**Actions → Публикация на PyPI → Run workflow**) принимает
версию без `v` (`0.4.0-beta.1` или `0.4.0b1`) и индекс: по умолчанию
TestPyPI. Тег `v<версия>` должен уже указывать на вершину `main`. Ручной
запуск не ждёт `release.yml` — это обходной путь, если автоматическая
проверка релиза не запускалась. Для проверки удобно сначала отправить версию
на TestPyPI (например `0.4.0b1`), а затем на PyPI.

Версию на PyPI нельзя перезаписать. При ошибке в опубликованном файле
выпускайте следующий номер или отзывайте версию через yank; тег не удаляйте —
он объясняет, из какого коммита собран файл. Пробный выпуск на TestPyPI
не занимает номер на PyPI.


## Пакетные менеджеры: Homebrew и Scoop

Версионный релиз автоматически обновляет два внешних репозитория:

- `zmlsaggg/homebrew-leksika` — `Formula/leksika.rb` (macOS arm64, macOS x64, Linux x64);
- `zmlsaggg/scoop-leksika` — `bucket/leksika.json` (Windows x64).

За это отвечает задание `update-package-managers` в
`.github/workflows/release.yml`. Оно запускается только по тегу `v*`, строго
после успешного `publish-versioned`, и только для стабильной версии: суффиксы
`-alpha`, `-beta`, `-rc` в tap и bucket не попадают. Задание правит версию,
ссылки на архивы и SHA-256, затем коммитит и отправляет изменения в `main`
обоих репозиториев сообщением `chore: update leksika to v<версия>`. Если файлы
уже описывают нужную версию, коммит не создаётся.

Сами суммы берутся из опубликованного `zz-SHA256SUMS.txt`: сначала задание
сверяет артефакт, затем скачивает те же файлы из релиза и сравнивает суммы —
так ссылки в формуле и манифесте указывают на реально существующие архивы.
Формула и манифест правятся точечно, остальной текст сохраняется; после записи
проверяются повторным разбором JSON и, если на раннере есть Ruby, командой
`ruby -c`.

Отдельного запуска не требуется. Повторить обновление для уже вышедшей версии
можно кнопкой **Re-run failed jobs** у задания: версия берётся из тега, повторный
запуск идемпотентен.

## Проверка файлов в VirusTotal

После публикации релиза отдельное задание `virustotal` отправляет двоичные
файлы выпуска (`.exe`, `.apk`, `.zip`, `.tar.gz`) в VirusTotal и дописывает в
описание релиза сворачиваемый блок со ссылками на отчёты. Задание стоит
последним в цепочке и запускается только по тегу `v*`.

Оно намеренно ни на что не влияет: при любой ошибке (нет ключа, лимит API,
недоступная сеть) печатается предупреждение, а выпуск остаётся как есть. Уже
опубликованный релиз не отменяется и не переписывается.

Скрипт свой — `проверка/virustotal.py`, только стандартная библиотека, без
сторонних экшенов: так цепочка выпуска не зависит от чужого кода. Темп
отправки — один файл в 16 секунд, потому что бесплатный ключ даёт 4 запроса в
минуту. Повторный запуск задания не задваивает блок: перед записью скрипт
проверяет, нет ли заголовка «Проверка безопасности (VirusTotal)» в описании.

### Разовая настройка секрета `VT_API_KEY`

1. Зарегистрируйтесь на <https://www.virustotal.com> и откройте
   **API key** в профиле.
2. В репозитории: **Settings → Secrets and variables → Actions → New
   repository secret**, имя ровно `VT_API_KEY`.
3. Секрет необязателен. Без него задание завершится за секунды с сообщением
   «VirusTotal пропущен».

Файлы больше 32 МиБ API принимает только по публичной ссылке, которой до
выпуска ещё нет; такой файл пропускается с предупреждением, а не роняет
проверку. Самотест без сети: `python3 проверка/virustotal.py самотест`.

### Разовая настройка секрета `CROSS_REPO_TOKEN`

Запись в чужие репозитории идёт токеном из секрета `CROSS_REPO_TOKEN`. Это
fine-grained personal access token, а не `GITHUB_TOKEN`: последний действует
только внутри `zmlsaggg/Leksika`.

1. Откройте **Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → Generate new token**.
2. **Repository access → Only select repositories**: `zmlsaggg/homebrew-leksika`
   и `zmlsaggg/scoop-leksika`.
3. **Permissions → Repository permissions → Contents: Read and write.** Больше
   ничего не нужно: задание коммитит прямо в `main`, pull request не создаёт.
   `Workflows` не требуется, метаданные доступа только читаются.
4. Срок действия — по политике проекта; после истечения задание упадёт с
   сообщением о токене, и его нужно выпустить заново.
5. Сохраните токен в **zmlsaggg/Leksika → Settings → Secrets and variables →
   Actions → New repository secret** с именем ровно `CROSS_REPO_TOKEN`.
   Секрет репозитория, а не окружения: задание не использует `environment`.

Читать релиз токен не нужен — файлы релиза публичные, поэтому в конфигурацию
клонирования он не попадает и передаётся только аргументом к `git push`.
Отдельный шаг проверяет, что в `.git/config` клонов не осталось токена.

Если токена нет, задание падает с понятным сообщением до любых изменений;
публикация на PyPI от этого не зависит: `publish.yml` ждёт только
`publish-versioned`, а не успех всего `release.yml`.

### Ручное обновление

Скрипт можно запустить локально — он не требует сети, если указать файл сумм:

```sh
git clone https://github.com/zmlsaggg/homebrew-leksika /tmp/tap
git clone https://github.com/zmlsaggg/scoop-leksika /tmp/scoop
python3 packaging/update_package_managers.py 1.0.0 \
  --sums zz-SHA256SUMS.txt --homebrew /tmp/tap --scoop /tmp/scoop --dry-run
```

Уберите `--dry-run`, чтобы записать файлы, затем проверьте `git diff` и
отправьте изменения сами. Флаг `--download` скачивает `zz-SHA256SUMS.txt` из
GitHub Release нужного тега. Проверка самого скрипта — без сети и секретов —
запускается в CI: `python3 проверка/менеджеры_пакетов.py`.

## GitHub Releases и GitHub Packages

Это два разных способа распространения:

- **GitHub Releases** — версии программы, привязанные к Git-тегу. Сюда прикладываются готовые установщики и архивы: например, Windows `.exe`, архив Linux/macOS и файл `SHA256SUMS.txt`.
- **GitHub Packages** — реестры для конкретных форматов пакетов. GitHub поддерживает npm, RubyGems, Maven/Gradle, NuGet и Container/OCI (Docker). Это не универсальное хранилище для произвольных `.exe` и `.zip`.

У Лексики пока нет собственного пакетного менеджера и совместимого с GitHub Packages формата. Поэтому готовые сборки следует публиковать через **Releases**; раздел Packages пока можно оставить пустым. Публиковать контейнер в GHCR имеет смысл только при появлении отдельного официального Docker-сценария — он не заменит обычный установщик.

Документация GitHub:
- [О GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
- [О GitHub Packages и поддерживаемых реестрах](https://docs.github.com/en/packages/learn-github-packages/introduction-to-github-packages)

Установщик содержит стандартный ресурс версии (`сборка/установщик.rc`) и не
использует UPX; версия ресурса 0.1.0.0 — версия загрузчика, а не номер Git-тега.
При подозрении на ложное срабатывание отправьте **конкретный SHA-256 и файл**
через [Microsoft Security Intelligence](https://www.microsoft.com/en-us/wdsi/filesubmission)
и, при необходимости, производителям других антивирусов. Результат и сроки
зависят от вендора. Метаданные не удостоверяют издателя и не гарантируют,
что браузер или антивирус перестанет предупреждать.

### Дополнительные компоненты установщика

Графический установщик предлагает `D:\Лексика` или `%LOCALAPPDATA%\Лексика`,
если диск D отсутствует. Папку можно выбрать в проводнике; ранее выбранный путь
запоминается в HKCU. Для новой установки нужна пустая папка. Деинсталлятор
удаляет файлы текущего пакета и сохраняет посторонние файлы. Он не удаляет
автоматически оставшиеся файлы старых версий. Графический установщик показывает
фактическую папку,
прогресс по объёму распакованных файлов и приблизительное оставшееся время
распаковки; финальные 10% отведены самопроверке и настройке. Скорость диска и
самопроверка влияют на общее время. Тихая установка не открывает страницы и не
изменяет хранилище сертификатов.

Необязательные пункты по умолчанию выключены. Если выбрать модель, после
успешной установки откроется отдельное окно загрузки. GigaChat 3.1 10B Q4_K_M
(6,47 ГБ) и YandexGPT 5 Lite 8B Q4_K_M (4,92 ГБ) скачиваются из официальных
репозиториев Hugging Face по закреплённым ревизиям. Потребуются интернет и
свободное место в `%LOCALAPPDATA%\Лексика-модели`; эти файлы не удаляются при
удалении Лексики. Сценарий проверяет размер и закреплённый SHA-256, сохраняет
данные во временный файл и переименовывает только после проверки. Повторный запуск
использует проверенный готовый файл; прерванную загрузку начинает заново.

Установка весов не устанавливает llama.cpp и не выбирает модель автоматически.
Установите совместимый `llama-cli`, затем настройте путь и режим внешней модели
через `Leksika настройка` (инструкции также выводятся в окне загрузки). У моделей
разные лицензии: [GigaChat](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF)
и [YandexGPT](https://huggingface.co/yandex/YandexGPT-5-Lite-8B-instruct-GGUF/blob/main/LICENSE).
Ручной повтор: `питон\python.exe лексика\скачать_модели.py gigachat yandex`
из папки установки. Скрипт не является нативным runtime и использует встроенный Python.

Пункт сертификатов открывает официальную страницу Госуслуг после отдельного
предупреждения: корневой сертификат расширяет доверие системы. Автоматический
импорт сертификатов пока не реализован. Тихая установка не открывает страницы,
не загружает модели и не меняет хранилище сертификатов.

Начиная с этого выпуска имена публичных файлов `leksika.exe`, `SHA256SUMS.txt`
и `checksums.txt` в обновляемом канале заменяются на `00-Leksika-Windows.exe`,
`zz-SHA256SUMS.txt` и `zz-checksums.txt`; старые прямые ссылки на них перестанут
работать. Внутреннее имя проверенного Windows EXE не меняется.
