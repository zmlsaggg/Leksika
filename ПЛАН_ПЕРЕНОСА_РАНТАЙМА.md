# План создания самостоятельного движка Лексуса

**Цель:** Лексика должна исполнять собственные программы без Python и не должна зависеть от семантики C или другого языка реализации. Пользователь получает готовый движок; ему не нужны Python, C-компилятор или сторонняя среда.

Нормативная основа: [документы/КОНТРАКТ_ДВИЖКА.md](документы/КОНТРАКТ_ДВИЖКА.md). Именно там фиксируются типы значений, арифметика, текст, коллекции, области видимости, ошибки и смысл команд машины.

## 1. Честное состояние основной ветки

На 11 ноября 2026 года в `main`:

- `ядро/лексус.c` содержит загрузочный нативный слой: проверку UTF-8, токенизацию, словарь служебных форм и первую генерацию склонений. Он не исполняет программы Лексики целиком.
- `лексика/*.lek`, `лексус.lek` и часть служебных сценариев фактически содержат код на синтаксисе Python. Переходный загрузчик читает их и запускает через `compile/exec` Python.
- `лексика/байткод.lek` создаёт команды для операторов, но часть операндов по-прежнему является узлами дерева грамматики.
- `лексика/машина.lek` передаёт вычисление выражений старому исполнителю и имеет запасной путь для вызовов через дерево. Значит, полной самостоятельной виртуальной машины пока нет.
- Установщик Windows включает встроенный Python; Linux/macOS требуют Python. Полная независимость пока не достигнута.

Это не недостаток названия языка, а конкретный долг переноса. Не называем его решённым, пока не исчезнет из исполняющего пути.

## 2. Принципы миграции

1. Не заменять Python на Rust, Go или C как постоянный язык движка. Это только перенесло бы зависимость.
2. C11 разрешён как временная загрузочная ступень для сборки первого самостоятельного исполняемого ядра. Он не определяет виды значений, правила чисел, синтаксис или стандартную библиотеку Лексики.
3. Python остаётся временным сравнительным эталоном для старых тестов, но новые правила берутся из контракта и тестов Лексики.
4. Дерево грамматики не должно попасть в байткод или в виртуальную машину. Компилятор полностью переводит выражения и действия в собственные команды.
5. Низкоуровневые функции ОС доступны только через явную стандартную среду. Они не просачиваются в семантику.
6. Каждая новая часть сначала получает тесты, затем реализацию. Переходный и новый движок сравниваются на одном наборе программ.

### Этап 2 — полная сборка в команды

- Каждое выражение компилируется в последовательность команд.
- Константы и имена располагаются в отдельных таблицах.
- У команд есть только фиксированные операнды: индексы, числа, адреса и коды действий.
- В байткоде нет узлов дерева, объектов компилятора, указателей или функций хост-языка.
- До исполнения проверяются адреса переходов, индексы таблиц и структура программы.

Критерий: после компиляции дерево грамматики можно освободить — исполнение от него не зависит.

### Этап 7 — удалить переходную реализацию

Только после прохождения общего набора тестов:

- убрать Python из установщиков и обычного запуска;
- удалить Python-модули-переходники и запасной исполнитель;
- исключить C-компилятор из требований установки и повседневной сборки пользователя;
- оставить воспроизводимый процесс самосборки и проверочные эталоны.

## 4. Что не делать

- Не переписывать всё сразу и не ломать рабочие программы ради чистоты исходников.
- Не добавлять команды VM, которые содержат объекты AST или вызывают методы старого исполнителя.
- Не считать отдельный C-лексер или нативное склонение самостоятельным интерпретатором.
- Не переносить поведение Python или C без письменного решения о его смысле в Лексике.
- Не менять синтаксис пользовательских программ только потому, что его проще разобрать на языке реализации.

## 5. Приёмка

Python удаляется только после того, как новый движок:

1. проходит весь функциональный набор тестов;
2. исполняет все примеры и программы из руководства;
3. собирает и исполняет байткод без старого дерева и исполнителя;
4. работает на Windows, Linux и macOS без установленного Python;
5. воспроизводимо собирает сам себя;
6. проходит проверки ошибок, границ памяти, путей и разрешений среды.

До этого момента статус проекта — **переход к самостоятельному движку**, а не завершённая независимость.
