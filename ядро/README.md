# Нативное ядро Лексуса

Нативный загрузочный слой сейчас реализуется на C11 и использует только
стандартную библиотеку C. Он не исполняет программы Лексики целиком.
C11 — временная ступень сборки первого движка, а не окончательный язык
реализации и не источник правил семантики. Python пока остаётся в рабочем
исполняющем пути старой версии.

## Сборка

```sh
make -C ядро
make -C ядро test
```

На Windows с MinGW:

```sh
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic -o лексус-ядро.exe ядро/лексус.c
лексус-ядро.exe самопроверка
```

## Русские команды

```sh
лексус-ядро версия
лексус-ядро самопроверка
лексус-ядро проверить программа.lek
лексус-ядро разобрать программа.lek
лексус-ядро склонять книга ж
```

Старые флаги `--version`, `--self-test`, `--check-utf8` и `--lex`
сохранены как совместимые псевдонимы.

## Реализовано в нативном загрузочном анализаторе

- Проверка корректности UTF-8.
- Первичная токенизация кириллического исходного кода.
- Выделение блоков `речь ... конец речи`.
- Нативная таблица 266 служебных словоформ с учётом регистра.
- Сведение известных служебных форм к леммам.
- Первый морфологический анализатор русских падежных окончаний.
- Нативная генерация 12 регулярных форм существительного: шесть падежей в единственном и множественном числе.
- Начальные правила для существительных на `-а/-я`, `-о/-е/-ё`, согласную, `-й` и `-ь`.
- Учёт рода для мягкого знака и одушевлённости в винительном падеже.
- Нормализация русских заглавных букв в нижний регистр для морфологического разбора.
- Встроенные проверки форм «счётчику», «СУММУ», «перечня», а также склонения «книга», «студент» и «окно».

Нативный генератор пока покрывает только регулярные шаблоны и не является
полной русской морфологией. Нерегулярные чередования, беглые гласные,
исключения, несклоняемые слова и контекстная дизамбигуация ещё не перенесены.
Анализатор окончаний может возвращать несколько кандидатов — это ожидаемо
для суффиксного разбора без контекста.

## Модель значений — этап 1

В `значения.h` и `значения.c` появился отдельный загрузочный модуль собственных
значений Лексики. Он пока не подключён к исполнению пользовательских `.lek`
программ и не заменяет старого исполнителя. Его назначение — зафиксировать и
проверить семантику языка независимо от `int`, `double`, `char*`, `list` или
`dict` хост-языка.

Сейчас реализовано:

- собственные виды `ничто`, `логика`, `число`, `речь`, `перечень`, `словарь`,
  `правило` и `действие среды`;
- целые числа произвольной длины и точная десятичная арифметика на строках
  десятичных цифр: сложение, вычитание, умножение и деление;
- деление с точностью до 34 знаков и округлением к ближайшему, при равенстве —
  к чётному;
- отдельные значения `да`/`нет`, без смешивания логики с числом;
- UTF-8-речь с явной длиной в байтах, поддержкой U+0000 и длиной в кодовых
  точках Unicode;
- изменяемые перечни и словари с общими ссылками, чтением, записью и удалением;
- ключи словаря только трёх видов: речь, число и логика;
- структурное равенство перечней и словарей; порядок важен для перечня,
  но не важен для словаря;
- запрет циклических вложений, чтобы выбранное подсчётное управление ссылками
  не оставляло недоступные циклы в памяти;
- собственные коды ошибок для неверных значений, деления на ноль, UTF-8,
  ключей, отсутствующих элементов и нехватки памяти.

Проверки модуля собраны в `значения_проверка.c`. Команда
`make -C ядро test` запускает и самопроверку старого нативного анализатора,
и отдельный набор модели значений. Новый модуль локально собран GCC с
`-std=c11 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined`:
**49 проверок прошли, 0 провалено**. Это результат только для модуля значений,
а не подтверждение всей VM. Перед слиянием требуется выполнить общий `make`
на целевой Windows/MSYS2-среде.

## Необязательный корпоративный TLS-инструментарий

`сертификаты.c` — отдельная утилита OpenSSL 3 для организаций. Она не
подключена к основной VM и не меняет её зависимости. Сборка по запросу:

```sh
make -C ядро tls-tools
make -C ядро tls-test
./ядро/лексус-сертификаты профили
```

Возможности: чтение X.509 PEM/DER, проверка цепочки от явно выбранного CA,
проверка PKCS#12 с вводом пароля без отображения, проверка соответствия
закрытого ключа сертификату, TLS-проверка hostname и mTLS. Закрытый ключ
не экспортируется в файл. По умолчанию утилита использует пути доверия
OpenSSL; добавочный CA-файл передаётся явно. Никакие корневые сертификаты
автоматически не устанавливаются.

Для Russian Trusted CA используйте только официальный набор Госуслуг:
https://www.gosuslugi.ru/crt. Для Sber API сверяйте сертификат и `clientId`
с актуальной документацией и личным кабинетом банка.

**ГОСТ TLS не реализован этой OpenSSL-утилитой.** Для ГОСТ-профиля нужен
внешний совместимый и сертифицированный криптопровайдер (например,
КриптоПро CSP) с поддерживаемой интеграцией. Инструмент не заменяет СКЗИ,
не формирует квалифицированные подписи, не проверяет отзыв сертификатов
OCSP/CRL и не подтверждает соответствие требованиям регуляторов.

Подробности — в [документе корпоративного TLS](../документы/КОРПОРАТИВНЫЙ_TLS.md).

## Следующий этап

1. Подключить собственную модель значений к компилятору выражений.
2. Перевести выражения из дерева грамматики в команды без AST-объектов в байткоде.
3. Перевести виртуальную машину на прямое исполнение этих команд, без вызовов
   старого исполнителя.
4. Затем переносить лексер, морфологию, грамматику и стандартную среду.

Переходная Python-реализация служит сравнительным эталоном. C11 используется
только как временная загрузочная ступень: семантика языка не должна зависеть
от `int64_t`, `double`, указателей, исключений или иных особенностей C.
