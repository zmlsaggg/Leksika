# Подключение сообщества Supabase

Сайт — статический GitHub Pages, не Next.js. Здесь используется браузерный `@supabase/supabase-js`, а не `@supabase/ssr`, Server Components и middleware из Next.js. SDK сохраняет и обновляет сеанс на клиенте. Публичные URL и publishable key находятся в `сообщество-исходник.js` и доступны посетителям: безопасность зависит от RLS, а не от сокрытия ключа. Никогда не добавляйте service-role/secret key или OAuth client secret в сайт или Git.

## Подготовка проекта владельцем

1. В SQL Editor именно нужного проекта запустите `supabase/схема.sql` **один раз**, предварительно ознакомившись с ним. Скрипт создаёт новые таблицы и политики; для существующих таблиц нужна отдельная миграция. Проект по предоставленному URL может быть ещё не настроен: из этой среды схема не применялась.
2. В Supabase Auth включите GitHub provider и настройте OAuth app в GitHub. Client ID и client secret задаются только в настройках Supabase. В GitHub callback URL укажите тот, что показывает Supabase (обычно `https://<project-ref>.supabase.co/auth/v1/callback`).
3. В Auth URL Configuration настройте Site URL и разрешите redirect URL для страниц сайта (`https://leksika.gleeze.com/**` и необходимые адреса предпросмотра). Вход возвращает пользователя на страницу, откуда он начал. Не используйте слишком широкие шаблоны для production. Проверьте, что GitHub provider включён. RLS для записи требует JWT с provider `github`.
4. Проверьте на двух независимых аккаунтах вход, публикацию и повторную жалобу. Для проверки автоматического скрытия потребуются пять разных GitHub-аккаунтов. Убедитесь, что анонимный и другой пользователь не могут менять авторов, скрывать или удалять записи через API.

Для обновления браузерной сборки: `npm ci && npm run build:community`. Сборка хранится в репозитории для статического Pages; CI проверяет её соответствие исходнику. `@supabase/ssr` и Next.js не нужны на этом сайте.

## Модерация и ограничения

- Пять разных авторизованных пользователей могут по одному разу пожаловаться на чужую программу или тему. На пятой жалобе транзакционный триггер **скрывает**, а не уничтожает запись: это позволяет администратору проверить злоупотребление и восстановить материал. Это не проверка обоснованности жалоб; пять поддельных аккаунтов могут скрыть материал. Нужны политика злоупотреблений, мониторинг и ограничение частоты на сервере.
- Администратор может найти и удалить запись или восстановить её в Supabase Dashboard / SQL Editor, используя административный доступ вне браузера. При восстановлении сперва удалите жалобы соответствующей записи в административном интерфейсе, затем снимите `скрыто`; иначе следующая жалоба снова скроет запись. Удаление записи каскадно удаляет её жалобы. Не выдавайте пользователям доступ администратора для этого.
- Веб-клиент не выполняет опубликованные исходники; они отображаются текстом и скачиваются. Это не полноценная песочница для недоверенных программ. Публичные программы/темы доступны всем, счётчики профиля считают только видимые записи, ответы в темах и роли администраторов в интерфейсе пока не реализованы.
- Необходимо отдельно настроить резервные копии, политику приватности, допустимый контент, лимиты Auth/API и наблюдение за проектом. Без развёрнутой SQL-схемы и настроенного GitHub OAuth формы не заработают. Нет гарантии защиты от массовой регистрации и накрутки жалоб.
