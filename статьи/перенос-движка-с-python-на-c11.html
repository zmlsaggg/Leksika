Дорога с Python
на C11

У Лексики сегодня две реализации. Одна работает целиком, но написана на Python. Вторая написана на C11, но пока исполняет только подмножество языка. Этот текст — карта границы между ними, без округлений в удобную сторону.

Автор: zmlsaggg · 16 ноября 2026 · Чтение: 7 минут · Русский / Движок

Почему движку вообще нужен свой движок

Лексика задумана как самостоятельный язык, а не как надстройка над чужим. Значит, смысл значений, арифметики, сравнений, областей видимости и ошибок должен определяться правилами Лексики — а не поведением Python и не особенностями C. Пока источником истины остаётся хост-язык, любой его апгрейд или другой интерпретатор по умолчанию меняет поведение вашей программы.

Переходный этап неизбежен: сначала нужно, чтобы язык вообще работал, и только потом — чтобы работал на своём. Поэтому в репозитории одновременно живут два слоя.

Слой первый: переходный runtime

Файлы лексус.lek и лексика/*.lek фактически написаны на синтаксисе Python. Расширение .lek само по себе не делает их программами на языке Лексика — загрузчик читает их и передаёт встроенному компилятору Python. Это сделано сознательно и описано в контракте движка.

Именно этот слой исполняет язык целиком: полную морфологию, падежное разрешение, словари, модули, заплатки, установщик. Именно его получает пользователь из установщика Windows и из установить.sh.

Слой второй: нативное ядро

Каталог ядро/ — компилятор и виртуальная машина на C11. Путь исполнения в нём короткий и явный:

КОНВЕЙЕР НАТИВНОГО ЯДРАисходник .lek (UTF-8)
   → лексер
   → разбор поддерживаемых конструкций и русских имён
   → таблица точных числовых констант и регистровые инструкции
   → проверка каждого opcode, регистра и индекса константы
   → исполнение в собственной VM с лимитом шагов

Важная деталь: после компиляции VM работает только с инструкциями, константами и регистрами. Дерево разбора и объекты AST в неё не передаются. Числа считаются собственной десятичной арифметикой, а не типом double, поэтому 0.1 + 0.2 не превращается в 0.30000000000000004, и целые значения не переполняются на границе машинного слова.

Что уже поддерживается

  • объявление пусть имя равно выражение и изменение увеличить/уменьшить/умножить/разделить;
  • ветвления если … то … иначе если … иначе … конец если;
  • циклы пока, счётные повторить N раз, прервать и продолжить, включая вложенные;
  • обход перечней для каждого имя из перечень повторять;
  • правила с параметрами и вернуть, вывод сказать, ввод спросить;
  • числа цифрами и словами, речь в блоках речь … конец речи, соединение речи;
  • сравнения, и/или, значения да, нет, ничто, утверждения почему.

Чего в нём ещё нет

  • интерполяции выражений внутри речи, словарей, модулей;
  • полного падежного разрешения имён — в этом слое имя нужно указывать точно;
  • файловой стандартной библиотеки и системных команд;
  • оптимизирующего IR и нативных бэкендов: C11 здесь загрузочная ступень, а не конечная цель.

У первого среза есть и технические лимиты: не более 254 переменных на программу, вложенность управляющих блоков до 128 уровней, отсутствие короткого замыкания у логических операций. Каждый лимит — это явная диагностика, а не молчаливое падение.

Почему не «просто переписать»

Язык на ходу переписать нельзя: им пользуются, у него есть установщик, примеры, документация и тесты. Поэтому перенос идёт кусками, и каждый кусок должен пройти собственные проверки. Отсюда правила, которые проект держит сознательно:

  • Сначала смысл, потом скорость. Быстрый код не оправдывает изменение результата программы.
  • Совместимость проверяется примерами. Переходная версия — эталон для сравнения, но не источник новых правил.
  • Никакой утечки устройства машины в язык. Пользователь не видит указателей, адресов, размеров машинных слов и исключений хост-языка.
  • Нет обязательного языка реализации. Python, C11, Rust или Go не назначаются постоянной основой движка.
ЧЕСТНЫЙ СТАТУС

Нативный движок пока не исполняет .lek целиком. Основная грамматика, исполнитель и сборщик Windows всё ещё используют Python. Режим нативно выбирается явно и не переключается на Python после ошибки: если ядро не собрано, запускатель честно сообщит об этом.

Как это проверить самостоятельно

Утверждения выше проверяются командами из репозитория, а не репутацией автора:

СБОРКА И ПРОВЕРКА НАТИВНОГО ЯДРАmake -C ядро native
./Leksika нативно запустить примеры/нативная_vm.lek
make -C ядро test
python3 проверка/сопоставление_движков.py

Ожидаемый вывод примера — одна строка Готово!. Полный набор тестов проверяет приоритет операций, деление на ноль, числительные словами, речевые литералы, циклы с нулевыми и дробными счётчиками, локальную область переменной цикла и отказ от необъявленных или латинских имён.

Что впереди

Порядок этапов зафиксирован в документах, чтобы прогресс можно было сверять с планом, а не с обещаниями: собственные значения и проверки контракта, бинарный индекс словаря, удаление Python из запуска, перенос bootstrap-компилятора на саму Лексику, оптимизирующий IR и нативные бэкенды для x86-64 и AArch64, затем память, FFI, потоки и пакеты для Windows, Linux, macOS и Android.

Самохостинг — компилятор, написанный на Лексике, — остаётся дальней целью. До неё в проекте не будет ни одной строки, утверждающей обратное.
